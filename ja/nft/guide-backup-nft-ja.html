Foundation終了前にNFTを保存する方法

マーケットプレイスが閉鎖されても作品が失われないようにするためのステップバイステップガイドです。ブロックチェーンは記憶しますが、ファイルは誰かが支え続ける必要があります。

著者: Ernesto Cisneros Cino · 作曲家、クリプトアーティスト、Impulses.art 設立者 · 2026年4月

Foundationが終了します。 トークンはブロックチェーン上に永遠に残りますが、作品を構成するファイル（画像、動画、メタデータ）はIPFS上に存在し、Foundation のノードにピンされています。これらのノードがいずれオフラインになると、リンクは機能しなくなり、作品は視覚的に孤立したトークンになります。オンチェーンの情報はそのまま残りますが、作品の視覚的要素は失われる可能性があります。

このガイドは、独立した分散型ピニングサービスを使って、作品全体を保存する方法を一から説明します。費用はかかりません。完了後、作品は明日閉鎖するかもしれない企業ではなく、ご自身が管理するインフラによって守られます。

作品の数によって30分から2時間ほどかかります。大切な作品を次の世代へ残すための時間として、十分に価値のある作業です。

ステップ 01

実際に何をするのか

作業を始める前に問題と解決策を理解しておくと、途中で迷わずに済みます。

問題

Foundationで作品をミントした際、スマートコントラクトはEthereum上にCID（Content Identifier、コンテンツ識別子）への参照を記録しました。このCIDはIPFS上のメタデータJSONファイルを指しています。そのJSONには作品のタイトルや説明が含まれ、さらに別のCIDを介して実際の画像または動画ファイルを指しています。

トークン自体は永続的です。しかしCIDで参照されるファイルは、IPFSのノードがピンして保持し続けている間だけ存在します。Foundationはこれらのファイルを自社のノードにピンしてきました。そのノードが停止し、他に誰もファイルをピンしていない場合、ファイルはネットワークから消失します。

解決策

同じCIDをご自身のノード（実際にはノードとして機能する無料サービス）にピンします。これはファイルをどこかに複製する作業ではなく、同じIPFSネットワーク内で、ファイルの存在を補強する行為です。CIDは変わらず、作品も変わりませんが、冗長性が加わります。ファイルはFoundationのノードとご自身のノードの両方に存在することになります。

Foundationがノードを停止しても、ご自身のノードは稼働し続けます。IPFSのリンクは機能し続け、作品はマーケットプレイスの終了後も存続します。

重要

Ethereum上のトークン（所有権、取引履歴、販売記録）は危険にさらされていません。危険にさらされているのは視覚的・記述的な層です。このガイドはその層を守ります。

ステップ 02

なぜFilebaseを選ぶのか

Pinataは業界の先駆者でしたが、無料プランはこの用途には適さなくなりました。Filebaseは現実的な代替案です。

Pinataは、私たちが必要とする機能（Import from IPFS、既存のCIDをピンする機能）に料金を設定しています。無料プランではコンピュータから新しいファイルをアップロードすることしかできず、ネットワーク上に既に存在するCIDをピンすることはできません。

Filebaseは5GBのストレージ、最大1,000ファイル、専用ゲートウェイ、Import CID機能、すべてクレジットカード不要の無料プランに含まれています。Pinataの5倍の容量で、必要な機能に制限がありません。

Filebaseはさらに地理的に離れた3箇所での冗長性を採用しています。マーケティング用の言葉ではなく、実際の冗長性です。

ご参考までに

Pinataが悪いサービスというわけではありません。ただ、ミント済みの作品をピンするという用途が、現在のPinataのビジネスモデルでは有料プランに移行した機能です。Filebaseは同じ用途を無料枠で扱っています。

ステップ 03

Filebase無料アカウントの作成

5分、クレジットカード不要。

  1. filebase.comにアクセスし、Get Started FreeまたはSign Upをクリックします。
  2. メールアドレスを入力し、安全なパスワードを作成します。カード情報や請求情報は一切求められません。
  3. 届いたメールのリンクからアカウントを確認します。
  4. ユーザー名とパスワードでダッシュボードにログインします。

空のワークスペースが表示されます。インターフェースは英語のみですが、操作はシンプルです。

ステップ 04

アーカイブ用バケットの作成

バケットとは、ピンを保管するフォルダのようなものです。

  1. ダッシュボードのサイドメニューでBucketsをクリックします。
  2. Create Bucketをクリックします。
  3. ユニークな名前をつけます。例: your-name-nft-archive。バケット名はグローバルに管理されるため、既に使用されている場合は別の名前にする必要があります。
  4. NetworkでIPFSを選択します。SiaやそのほかのネットワークではなくIPFSを選んでください。Foundation のNFTにはIPFSが必要です。
  5. Createで確定します。
S3 Private と Public について

Filebaseは公開バケットが有料プランでのみ利用可能であるというメッセージを表示します。これは無視してS3 Privateのままにしてください。このメッセージはS3アクセス（Amazonのプロトコル）に関するものであり、NFTでは使用しません。ファイルはipfs.io、dweb.link、cloudflare-ipfs.comなどすべてのIPFSゲートウェイからCIDを使って公にアクセス可能です。バケットのPrivate設定はこれに影響しません。

ステップ 05

各作品のCIDを取得する

各作品には2つのCIDがあります。メタデータJSON用と、画像または動画ファイル用です。

方法1: Foundationから取得（まだアクセス可能な場合）

  1. Foundationのプロフィールで作品を1つ開きます。
  2. DetailsまたはToken DetailsタブにIPFSまたはMetadataリンクがあります。
  3. 次のような形式です: https://ipfs.io/ipfs/QmXX.../metadata.json。これを保存します。
  4. メタデータCIDは/ipfs/と/metadata.jsonの間の部分です: QmXX...

方法2: JSONを開いてメディアCIDを抽出

ブラウザでJSONを開きます。次のような内容が表示されます:

JSONメタデータ { "name": "作品名", "description": "...", "image": "ipfs://QmYY.../nft.mp4" }

imageフィールドの値（animation_urlの場合もあります）はipfs://で始まり、別のCIDが続きます。これがメディアCIDです。これも保存します。

シンプルな目録表を作成する

作品ごとに次の情報を記録します:

  • 作品のタイトル
  • メタデータJSONのCID
  • メディアファイル（動画または画像）のCID
  • コントラクトアドレスとTokenID（後でEtherscanで検索するため）

シンプルなスプレッドシートで十分です。Foundationにまだアクセスできるうちに作成してください。後になるとデータの取り出しが格段に難しくなる可能性があります。

ヒント

Foundationのプロフィールから目録を一括でコピーできる場合は、まとめて取得してください。Etherscanでご自身のウォレットを検索し、NFTでフィルタリングしてトークンを直接探すこともできます。

ステップ 06

FilebaseでCIDをピンする

ここが実際のバックアップが行われる段階です。FilebaseがIPFSネットワークからファイルを見つけ、自社のノードにコピーします。

作品ごとの手順

  1. バケット名をクリックして、作成したバケットを開きます。
  2. 3つの選択肢が表示されます: Import CID、New Folder、Upload。Import CIDをクリックします。
  3. フォームが開きます。最初の作品のメタデータJSON CIDを貼り付けます。
  4. わかりやすい名前をつけます。例: my-artwork-metadata.json。
  5. Search and Pinで確定します。

FilebaseがIPFSネットワーク上でCIDを検索し（数秒かかります）、自社のノードにピンします。ステータスはPinning（進行中、オレンジのアイコン）からPinned（確定、緑のアイコン）に変わります。

メディアファイルのCIDについても同じ作業を繰り返します:

  1. 再度Import CIDをクリックします。
  2. 動画または画像のCIDを貼り付けます。
  3. 名前: my-artwork-media.mp4（または適切な拡張子）。
  4. 確定します。

推奨される命名規則

後でバケットを探しやすくするため、一貫した名前を使います。推奨例:

  • 単独作品: artwork-title-metadata.json と artwork-title-media.mp4
  • コラボ作品: split-collaborator-name-title-metadata.json
  • 連番シリーズ: series-01-title-metadata.json、series-02-...（9点を超える場合は先頭にゼロをつけます）

小文字、スペースの代わりにハイフン、アクセントや特殊文字は使わないようにしてください。URLやファイルシステムの問題を避けられます。

所要時間

1つのピンは、小さなJSONなら数秒、重い動画なら数分かかります。10〜15作品の場合、40分から1時間程度の手作業を見込んでください。

良い点

Filebaseが既に他の場所でピンしているCID（他のアーティストが同じファイルをピンしていた場合など）をピンすると、ほぼ瞬時に完了します。IPFSはファイルを複製するのではなく、ファイルの存在を補強します。

ステップ 07

正常動作の確認

バックアップを完了とする前に、ファイルが実際に公開ネットワークからアクセス可能かを確認します。

確認 1: すべてPinned状態になっている

バケットのStatus列を見ます。すべてのファイルに緑のアイコンとPinnedラベルが表示されている必要があります。数分経ってもPinning（オレンジ）のままのファイルがあれば、もう少し待つかページを更新してみてください。

確認 2: 公開ゲートウェイからアクセスできるか

CIDを1つコピーし、次のURLに貼り付けます。[CID]の部分を実際のCIDに置き換えてください:

CIDテスト https://dweb.link/ipfs/[CID]

コンテンツ（JSONや動画）が表示されれば、ピンは分散型ネットワーク上で生きており、FoundationやFilebaseに依存せず、どのゲートウェイからもアクセス可能であることが確認できます。

確認 3: 容量の使用量が妥当か

バケットのStorageインジケーターを確認します。一般的なNFT動画は10〜80MBです。動画付きの作品が15点あれば、500〜800MB程度になります。無料プランの5GB制限には余裕があります。

制限に近づいた場合（作品数が多いか、動画が非常に重い場合）、重要度の低い作品はメタデータのみをピンし、動画は追加バックアップなしにしておくことを検討してください。それらの動画はしばらくの間、他のIPFSの公開ノードで保持されます。

ステップ 08

ウェブサイトのリンク更新

個人のウェブサイトやポートフォリオでNFTへのリンクを使っている場合、それらは変更が必要です。Foundationを指しているリンクは機能しなくなります。

置き換える対象

ウェブサイトで次のようなリンクを探します:

https://foundation.app/mint/eth/0x...../tokenID https://fnd-collections.mypinata.cloud/ipfs/QmXX.../metadata.json https://fnd-collections4.mypinata.cloud/ipfs/...

これらはすべて機能しなくなります。安定したIPFSゲートウェイのリンクに置き換える必要があります。

使用するリンク

作品ごとに3種類のリンクを推奨します:

1. メタデータ（作品の技術情報）:

https://dweb.link/ipfs/[CID_METADATA]/metadata.json

2. メディア（動画または画像）:

https://dweb.link/ipfs/[CID_MEDIA]/nft.mp4

3. Etherscan（オンチェーンでの所有権確認）:

https://etherscan.io/token/[CONTRACT]?a=[TOKEN_ID]

この3番目のリンクがFoundationへのリンクの代わりになります。以前はマーケットプレイスを指していた場所が、決して閉鎖されないEthereumの公開レジストリを指すことになります。

ゲートウェイについて

私はdweb.linkを使っています。Protocol Labs（営利企業ではなく財団）が運営しており、比較的高速で中立的です。有効な代替案: ipfs.io（同じ運営、時に遅い）、cloudflare-ipfs.com（高速ですが中央集権的な企業に依存）。どれでも機能します。大事なのはCIDです。

ステップ 09

作品がArweaveにある場合（バックアップ不要）

Foundationの作品の中にはIPFSではなくArweaveを使用しているものもあります。その場合は永続性が組み込まれています。

作品のメタデータを開いた際にURLがarweave.netで終わっているか、ハッシュのあとに.arweave.netが続いている場合、その作品はIPFSではなくArweave上にあります。

Arweaveは別の分散型ストレージネットワークで、異なるモデルを持っています。ミント時に一度だけ支払えば、ノードに継続的に支払う基金（エンダウメント）によって約200年間の保存が保証されます。

結論: 作品がArweaveにある場合、バックアップの必要はありません。永続性は構造的に保証されています。目録に記録して、次の作品に進んでください。

ステップ 10

Foundation完全終了前に

最後に行うべき作業です。

未売却作品の出品取り下げ

まだ購入者がいないFoundationの出品作品がある場合、閉鎖前に出品を取り下げることを検討してください。Foundationのエスクローコントラクトからトークンが解放され、ご自身のウォレット（またはミンターのウォレット）に戻されます。ガス代が少しかかりますが、閉鎖後の複雑な状況を避けることができます。

コラボレーターへの連絡

オンチェーンスプリットを含む作品がある場合、コラボレーターにもそれぞれの立場でバックアップを行うよう伝えてください。スプリットはコントラクトが存在する限り機能しますが、ファイルが残り続けるためには複数のノードによる支えが必要です。

キュレーション情報のエクスポート

Foundationはオンチェーンにない情報を保管しています。コレクターの名前を含む販売履歴、編集された作品説明、正確なオークション日時、入札、フォロワーなどです。これらはすべてFoundationとともに消失します。 閉鎖前にスクリーンショットを撮るか、できる限りエクスポートしてください。

ご自身の歴史を記録する

クリプトアートの分野に長年関わってきた方は、内側から経験した数少ない一人として、文化史の一章の証人です。覚えていることを書き留めてください。イベントの写真、コミュニティの名前、閉鎖されたプラットフォーム、禁輸国のアーティストが受けたBANなど。この物語のアーカイブは、CIDと同じくらい重要です。

作業が完了したら

すべての作品をピンし、公開アクセスを確認し、ウェブサイトのリンクを更新すれば、作品群はFoundationの終了を越えて残り続けます。作品は残ります。物語は続きます。

ステップ 11

いつかFilebaseが閉鎖したらどうなるか

もっともなご質問です。Foundationに依存しないためにバックアップするのに、単に別の会社に依存を移しているだけではないか、という疑問は自然です。

短い答え

Filebaseが明日閉鎖しても、ファイルは即座に消えることはありません。IPFSは単一の障害点ではなく、同じコンテンツを複製するノードの積み重ねによって機能しています。Filebaseの閉鎖はファイルのコピーの1つを取り除くだけで、すべてを取り除くわけではありません。

さらに、CIDは普遍的です。Filebaseに属しているわけではありません。明日別のプロバイダーでアカウントを作って同じCIDを貼り付ければ、数分でアクティブなバックアップが再び得られます。ステップ05で作成した目録があれば、移行は簡単です。

IPFSにおける永続性の実際の仕組み

IPFS上のファイルは、少なくとも1つのノードが能動的にピンしている間存在します。FilebaseがあなたのCIDをピンすると、そのノード（通常は異なる場所に3重に複製）がファイルを生かし続けます。

しかしファイルを持っているのはFilebaseだけではありません。誰かがIPFSゲートウェイを訪問してあなたの作品を読み込むたびに、そのゲートウェイが一時的にキャッシュします。すべてのやりとりが短命の複製を残します。Foundationも閉鎖までCIDをピンしたままです。ネットワークには自然な複製の慣性があります。

Filebaseが閉鎖する場合の3つのシナリオ

シナリオ1、事前告知を伴う閉鎖（想定される場合）: 信頼できるサービスは数週間から数ヶ月前に告知します。別のプロバイダー（4EVERLAND、Web3.Storage、Lighthouse）へ移行する時間は十分にあります。CIDの目録が既にあるので、移行はアカウントを作って同じCIDをインポートするだけで済みます。

シナリオ2、事前告知なしの突然の閉鎖: 可能性は低いですが、起こりうることです。他のノードがファイルを持っていない場合に限り、ファイルが失われます。何らかの活動があるファイルについては、これは統計的にまれです。

シナリオ3、他社による買収（最も一般的）: より大きな会社が小さな会社を買収し、新しい条件でサービスを継続します。移行の間もピンは有効なままです。最近の例: KnownOriginはeBayに買収され、ポリシーに大きな変更がありましたが、以前にミントされたファイルは技術的には引き続きアクセス可能でした。

堅実な戦略: 複数プロバイダーによる冗長性

哲学的に正しい姿勢は、Filebaseが閉鎖しないと信じ続けることではなく、Filebaseのみに依存しないことです。真の分散化には真の冗長性が必要です。段階的に実装できる4つの保護レベル:

レベル1、現在の状態: Filebaseでのアクティブなピン。5GB無料。標準的な用途をカバーします。

レベル2、並列の冗長性: 別のプロバイダーで2つ目の無料アカウントを開設し、同じピンを複製します。堅実な選択肢:

  • 4EVERLAND: 5GB無料、クリーンなインターフェース、別のプロバイダー。
  • Web3.Storage: Protocol Labs（IPFSの開発者）のサービス。5GB無料、組織として非常に安定しています。
  • Lighthouse: 永続ストレージの一括払いモデル。Filecoinを経済レイヤーとして使用します。

同じCIDを2つの異なるプロバイダーにピンしておけば、一方の閉鎖はもう一方に影響しません。これが分散化が可能にする本来の姿です。特定のプロバイダーに縛られないことです。

レベル3、ローカルの物理的複製: すべてのメディアファイルをハードドライブまたは外付けディスクにフォルダ別に整理してダウンロードします。公開リンクには使いませんが、世界中のすべてのノードが失敗しても、マスターデータを自分で保管できます。真摯なアーキビストが行う最後の砦のバックアップです。

レベル4、オプション・上級者向け: 自分のマシンでIPFS DesktopまたはIPFS CLIを使って自身のIPFSノードを稼働させます。最大の技術的自律性を得られます。ノードはコンピュータが起動している間だけ有効なので、管理型サービスを補完しますが、置き換えるものではありません。

実用的な推奨

現時点ではFilebaseだけで十分（レベル1）です。短期的な実際のリスクに対しては十分な対応です。Filebaseは2019年から稼働しており、現時点では他のサービスよりも組織として安定しているように見えます。

3〜6ヶ月後、強化したい場合は4EVERLANDまたはWeb3.Storageでアカウントを作り、ピンを複製します。すべてのCIDを含む目録が既にあるので、15分程度の作業で済みます。これで過度なエンジニアリングなしに真の冗長性が得られます。

ハードドライブへのローカル複製は時間がある時にすれば大丈夫です。急ぎではありませんが、やる価値はあります。自前のIPFSノードは、インフラの管理が好きな場合にのみ推奨します。

中央集権と依存の違い

中央集権と依存は別のものです。Filebaseは中央集権的なプロバイダー（民間企業、自社サーバー）ですが、Filebaseへの依存は切り離し可能です。CIDはIPFSの標準であり、目録はご自身のディスクにあり、いつでも別のプロバイダーに移行できます。Foundationへの依存とは根本的に異なります。Foundationの閉鎖はリンク、物語、プロフィール、コミュニティの喪失を意味しました。今回はどのような閉鎖があっても、不便ではあっても壊滅的ではありません。これが真の前進です。大切な作品を失わせないという責任を、ご自身の手に取り戻したということです。

FAQ

よくある質問

Foundationの閉鎖とNFT保存について、よく受ける質問への短く直接的な回答です。

Foundationが閉鎖すると私のNFTはどうなりますか?

トークンはEthereum上に永遠に残り、削除も変更もできません。危険にさらされるのはオフチェーンの層、つまりFoundationのIPFSノードに現在存在するJSONメタデータとメディアファイル(画像、動画)です。これらのノードがオフラインになると、他のサービスにピンしない限り、ファイルにアクセスできなくなる可能性があります。所有権は安全ですが、視覚的表現にはバックアップが必要です。

NFTを別のブロックチェーンに移す必要がありますか?

いいえ。FoundationがどうなってもNFTはEthereum上に残ります。Foundationはマーケットプレイスのインターフェースで、Ethereumが基盤のブロックチェーンです。オフチェーンのファイルをバックアップするだけで済み、トークン自体を移す必要はありません。

FilebaseはNFTバックアップに本当に無料ですか?

はい。5GBのストレージ、最大1,000個のピン付きファイル、専用のIPFSゲートウェイ、Import CID機能がすべてクレジットカード不要で無料です。Pinataが有料プランに移行した機能の組み合わせです。

IPFSのCIDとは何で、なぜ重要なのですか?

CID(Content Identifier)は、コンテンツに基づいてIPFS上のファイルを一意に識別する暗号学的ハッシュです。NFTのスマートコントラクトはメタデータを指すCIDへの参照を保持し、メタデータはメディアのCIDを指しています。CIDは、ノードがファイルをピンしている間だけコンテンツへ解決されます。ピンがなければ、トークンが存在してもコンテンツは表示されません。

Filebaseも閉鎖したらどうなりますか?

ステップ11で詳しく扱いました。要約: CIDは普遍的なので、目録を使って数分で別のIPFSプロバイダー(4EVERLAND、Web3.Storage、Lighthouse)へ移行できます。堅実性のために複数プロバイダーによる冗長性を使います。

Foundation閉鎖前に未売却のNFTを出品取り下げすべきですか?

推奨します。出品取り下げによってFoundationのエスクローコントラクトからトークンが解放され、ミンターのウォレットに戻されます。将来別の場所で再出品できるようになります。少しガス代がかかりますが、後の複雑な状況を避けることができます。

バックアップ全体のプロセスにどれくらい時間がかかりますか?

10〜15点のNFTの場合、30分から2時間を見込んでください。JSONメタデータは数秒でピンされます。動画ファイルはそれぞれ数分かかることがあります。CIDの目録が揃っていれば、繰り返し作業ですが複雑ではありません。

NFTがIPFSではなくArweaveにある場合はどうなりますか?

バックアップは不要です。Arweaveは設計上の永続ストレージを提供します。ミント時に一度支払い、ノードに継続的に支払う基金によって約200年間保存されます。

このガイドはFoundation以外のアーティストにも有効ですか?

はい。メタデータとメディアがIPFS上にあるEthereumのすべてのNFTに同じプロセスが適用されます。SuperRare、Zora、Objkt、KnownOrigin(閉鎖前)、Rarible: 流れは同じで、CIDの出所だけが異なります。

コレクターとして他のアーティストのNFTをピンできますか?

はい、推奨されます。CIDは設計上公開されています。収集したNFTをピンすることで、元のノードの障害からあなたのコレクションを守ることができます。直接の連絡先がある場合は、礼儀としてアーティストに知らせることを検討してください。

技術的拡張

自分のIPFSノードを持つ

このセクションは、技術的に慣れていて、さらなる自律性を求めるアーティストのためのものです。作品のバックアップ自体には必要ありません(Filebaseで十分です)。いかなるプロバイダーにも依存しないという考えに共鳴する場合、これがその道です。

自分のノードを持つということ

IPFSノードとは、ネットワークの一員として動作するコンピュータのことです。ソフトウェアをインストールすると、あなたのマシンはファイルをピンし、世界中に提供し、商業サービスに依存せず生かし続けることができます。プロバイダーの顧客からネットワークの正式な参加者になります。自分の作品を他者のサーバーに預けるのではなく、自分のインフラで守る姿勢への移行と言えます。

Filebaseとの主な違い: Filebaseではファイルを自社サーバーにピンしてほしいと企業に依頼します。自分のノードではあなた自身がサーバーです。

重要なトレードオフ

ノードはコンピュータが起動しており、インターネットに接続している間だけファイルを提供します。マシンを停止すると、ファイルはネットワークの他のノード(Filebase、公開ゲートウェイ、他のピニングサービス)に存在し続けますが、あなたは貢献を停止します。真の恒久的バックアップのためには、ノードはほぼ常時稼働している必要があります。

制御レベルに応じた2つの道

道A: IPFS Desktop(最もアクセスしやすい)

macOS、Windows、Linuxで他のプログラムと同じように設定できるグラフィカルアプリケーションです。セットアップ5分、視覚的なインターフェース、コマンドライン不要。実験と学習に最適です。

利点: 簡単なインストール、視覚的インターフェース、必要のないときはアプリを閉じられる。
欠点: 稼働中にRAMを消費する(200〜400MB)、誤ってアプリを閉じると停止する、コンピュータを停止すると可用性が失われる。

道B: 専用のRaspberry Pi(本格的)

Raspberry Piを購入し(ケース、電源、SDカード込みで約75〜120USD)、IPFSをインストールして、自宅でルーターに接続した状態で24時間稼働させます。LED電球並みの電力消費(5〜10ワット、月約2〜3USD)で専用の恒久ノードになります。

利点: 真の恒久ノード、メインコンピュータのリソースを消費しない、完全な技術的自律性。
欠点: 初期購入が必要、より複雑な技術的インストール(コマンドライン)、外部アクセスのためのルーター設定。

推奨

IPFS Desktopから始めてください。経済的な約束なしに概念を学べます。数週間使ってみて実際に使っていると感じ、本物の永続性が欲しくなったら、そのときに専用のRaspberry Piへの投資を検討します。

IPFS Desktopのステップバイステップ

ステップ1: インストーラーをダウンロード

ipfs.tech/install/ipfs-desktop/(プロジェクトの公式ドメイン)にアクセスします。OS用のインストーラーを選びます: macOS、Windows、Linux。

ステップ2: インストール

macOSでは.dmgを開いてアイコンをApplicationsにドラッグします。Windowsでは.exeを実行します。Linuxでは通常.AppImageです。macOSの初回起動時にシステムが未検証の開発者について警告を表示することがあります。システム環境設定からセキュリティを開き、手動で許可を与えてください。正常な動作で、ソフトウェアが危険というわけではありません。

ステップ3: 初回起動

アプリケーションを初めて開くと、3つのことが自動的に行われます。第一に、ノード用の暗号学的な一意のアイデンティティが作成されます(ネットワーク上でのノードの恒久的ID)。第二に、グローバルIPFSネットワークに接続し、数秒以内に数十から数百の接続されたピア(他のノード)が表示されます。第三に、5つのタブを持つインターフェースが開きます: Status、Files、Explore、Peers、Settings。

ステップ4: 最初のCIDをピン

Filesタブに移動します。上部にImportボタンがあります。クリックするとオプションメニューが展開されます。From IPFS(時にはAdd by CIDやImport from IPFSと表示される)を選びます。CIDを1つ貼り付けて確定します。

ノードがそのファイルを持つ他のノード(Filebase、公開ゲートウェイ、活動中のソース)からファイルのダウンロードを開始します。数秒から数分(サイズによる)でファイルがローカルにピンされます。その瞬間、あなたのコンピュータはそのCIDを支えるネットワークの一員となります。

ステップ5: 動作の確認

2つの簡単な確認。一つ目、Filesにピンのアイコンとダウンロードされたサイズが表示されるCIDが見えるはずです。二つ目、ブラウザで次を開きます:

ローカルゲートウェイ http://localhost:8080/ipfs/[your-CID]

このlocalhost:8080は、あなたのノード自身が立ち上げているローカルゲートウェイです。コンテンツが表示されれば、ノードがファイルをアクティブに提供していることになります。これが本当の技術的自律性です。

ステップ6: 残りの作品群をピン

目録のすべてのCIDでプロセスを繰り返します。10〜15点の作品の場合、接続に応じて30分から2時間を見込みます。

日常使用での実践的考慮事項

リソース消費: IPFS Desktopは稼働中に200〜400MBのRAMを使います。現代のコンピュータでは問題になりませんが、メモリが少ないマシンでは気になります。Settingsで制限を設定できます。

帯域幅: ノードはダウンロードだけでなく、ファイルを要求する他のノードへアップロードも行います。接続に制限がある場合はSettingsで制限を設定してください。一般的な家庭用接続では気にならないでしょう。

コンピュータの停止: CIDは他のノードがピンしている間ネットワーク上で生き続けます(Filebaseがバックアップとして残ります)。ノードは一時的に貢献を停止するだけです。再起動すると自動的に再開されます。

ディスクスペース: ピンされた各CIDはローカルディスクでそのサイズを占有します。計算: 500MBのFoundation作品群なら、ノードは500MBを占有します。大きなTezos作品群の場合は数GBになることがあります。ディスクに空きがあるか確認してください。

具体的に得られること

  • Filebaseからの真の独立: 明日Filebaseが閉鎖しても、ノードがアクティブならファイルは介入なしにアクセス可能なままです。
  • 仲介者なしの発行: 新作をサービスを経由せずにIPFSにピンしたい場合、ノードから直接行えます。
  • システムの技術的理解: 数週間でもノードを運用すれば、ほとんどのNFTアーティストが得ることのないエコシステムへの理解が得られます。
  • エコシステムへの貢献: 追加の各ノードがIPFSネットワーク全体を強化します。参加は自己防衛だけでなく、共同体への行動でもあります。

Raspberry Piへの自然な進化

IPFS Desktopを試した後、本物の永続性が欲しくなったら、自然な道は次の通りです:

  1. Raspberry Pi 4(4または8GB RAM)、電源、ケース、128GBのmicroSDカードを購入。合計で約100〜150USD。
  2. 自宅の一角でイーサネットケーブルを使ってルーターに接続。
  3. Raspberry Pi専用のチュートリアル(英語に豊富、一部日本語や中国語や西語)に従ってIPFSをインストール。
  4. 停電時にノードを常時稼働させるため、自動再起動を設定。
  5. 応用オプション: Raspberry Piを指す独自のサブドメイン(例: ipfs.yourartist.art)を設定して、自前のゲートウェイを持つ。

この最後のステップ、自分のドメインで自前のゲートウェイを持つことは、最大限の自律性です。dweb.linkやipfs.ioにも依存しなくなります。ウェブサイトのリンクはあなたのもの: ipfs.yourartist.art/ipfs/[CID]/file.mp4となります。

はっきりさせるため

自前のノードを持つことはFilebaseを置き換えるものでも、これまでの作業を無意味にするものでもありません。それを補完するものです。理想的な戦略はこれらを組み合わせます: 常時稼働の管理型バックアップとしてのFilebase、自分のインフラから補強するIPFS DesktopまたはRaspberry Piの自前ノード、最終手段のアーカイブとしてのハードドライブのローカル複製。3つの冗長な層、それぞれ異なる設計で守られています。
